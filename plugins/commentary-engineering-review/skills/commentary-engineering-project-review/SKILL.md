# Commentary Engineering Project Review

Use Review guide for the composed Project Review Session; Session remains the API/CLI identity. Individual PR, branch, draft and live preview objects remain Reviews. A package publishes immutable content and can be one guide target; publishing it does not create a guide or link a Project automatically. Keep direct review when a composed guide is unnecessary.

Start with the rendered walkthrough: purpose, architecture, alternatives, API/data flows, risks and limitations. Link multiple original PRs and pin exact package/source/requirement/evidence targets in an immutable Review Session manifest. Opening a historical merged PR must preserve that snapshot rather than substitute the latest branch.

Capture authorized selected source at an exact provider SHA and blob digest. Uploaded source keeps uploaded provenance. List lazy directories and bounded ranges; mark uncaptured, deleted, inaccessible and unresolved content explicitly. Link architecture/API occurrences to exact source/evidence targets and use native contextual threads for investigations.

Define acceptance requirements and actor-attributed claims. Attach inert reports as reported evidence, then request independent provider verification for the exact repository/SHA/run when supported. Passing CI establishes only that observed check; unavailable, mismatched, failed, stale and revoked receipts remain explicit. Request eligible human acceptance of one deliverable or an explicit selected Session subset, with exact targets, supporting evidence/requirement revisions and consequence. Do not broaden the selected scope to the whole Project. Read the aggregate and return awaiting_human when pending.
