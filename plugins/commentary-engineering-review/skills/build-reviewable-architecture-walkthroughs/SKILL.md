# Build Reviewable Architecture Walkthroughs

Build a navigable rendered overview of the user outcome, system boundaries and important flows. Scale detail to the requested review. Put an accessible textual explanation beside diagrams and link deeper pages by meaningful questions.

Ground diagram nodes, arrows and API claims in inspected source at pinned commits. Distinguish implemented paths from proposed or inferred paths. Label access boundaries, external providers, storage, async work and failure/retry paths only where supported. Mark uncaptured or denied source as unavailable rather than filling gaps from memory.

Use stable semantic page and section identifiers for native review anchors. Link original Resources without granting access. Capture selective relevant source; avoid publishing an entire repository or requiring every changed line to be read. Preserve source provenance, test command/run scope and explicit unresolved questions.

For requested publication and source/evidence relations use commentary-review-package-creation and commentary-engineering-project-review when available; use commentary-project-feedback-loop for immutable corrections. Uploaded reports remain claims, and only eligible humans accept exact revisions.

Read [source mapping](references/source-mapping.md) for diagrams and API links; see [worked example](references/worked-example.md) for a two-page walkthrough.
