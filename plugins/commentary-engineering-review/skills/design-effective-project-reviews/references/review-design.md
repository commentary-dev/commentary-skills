# Review design

An overview should explain purpose, before/after behavior, the requested judgment, exact revision and remaining questions. Choose depth by the reader's job: product implications for PMs; selective data flow, contracts and failure paths for engineers; provenance and bounded conclusions for evidence reviewers.

Use realistic examples alongside narrative. Give diagrams a textual equivalent and descriptive links. Put technical identifiers behind detail without hiding exact acceptance scope. If source is unavailable, state that constraint and request authorized inspection; do not paraphrase private titles into shared summaries.

Prefer native views for routine status and comparison. Reserve custom visuals for a specific comprehension gap and retain native fallback. Existing free organization/review workflows stay free; discover advanced Pro-preview capabilities instead of assuming an entitlement.

For returning readers, compare explicit immutable endpoints or the authorized saved-visit receipt. Separate Resume at the latest accessible composition from changes since that saved visit. Missing endpoints remain unavailable; do not silently replace the comparison. Explain material changes and exact acceptance currency separately.

Ask for acceptance of one deliverable or an explicit selected Session subset with its consequence and exact supporting evidence/requirement revisions. Keep the original scope visible when other guide targets change; agreement in a discussion or poll is not that Decision.

Feedback recovery: read current native comments, preserve authorship and unresolved discussion, revise immutable artifacts, then request a new exact human Decision if necessary. Previous acceptance remains historical. Do not label a change accepted because feedback was answered.
